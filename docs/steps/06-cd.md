# 06 — CD (deploy otomatis ke Kubernetes)

## Tujuan
Setelah CI hijau di `main`, versi baru otomatis di-deploy ke cluster kind, dan otomatis di-rollback bila gagal.

## File
`.github/workflows/cd.yml` — dipicu `workflow_run` dari workflow **CI** (hanya `push` ke `main` yang sukses), berjalan di **self-hosted runner**:
1. `kubectl set image deployment/app app=ghcr.io/<owner>/task-tracker:<sha>`
2. `kubectl rollout status --timeout=120s`
3. Jika gagal → `kubectl rollout undo`

## Menyiapkan runner (sekali, oleh Anda)
1. GitHub repo → Settings → Actions → Runners → **New self-hosted runner** (Windows), ikuti perintahnya.
2. Jalankan runner di laptop yang sama dengan cluster (`kubectl --context kind-task-tracker get nodes` harus berhasil di PowerShell; workflow memakai `shell: powershell`).
3. Settings → Actions → General: untuk repo **publik**, pilih *Require approval for all outside collaborators* dan jangan izinkan fork menjalankan workflow di runner ini.
4. Set paket GHCR `task-tracker` menjadi **public** agar cluster bisa menariknya tanpa credential.

## Verifikasi
Diuji lokal (logika deploy/rollback yang sama dengan workflow):
- Deploy dengan tag yang tidak ada → pod baru `ImagePullBackOff`, `rollout status` **timeout** setelah 45 detik.
- Selama rollout macet, `/health` tetap `200` (pod lama masih melayani — `RollingUpdate` tidak mematikan pod lama sebelum yang baru siap).
- `kubectl rollout undo` → image kembali `task-tracker:local`, rollout sukses, `/health` ok.
- `cd.yml` lolos `actionlint`.

Uji penuh di GitHub: ubah teks di `app/public/index.html`, push ke `main` → CI hijau → CD hijau → `http://tasks.localhost` menampilkan perubahan.

## Konsep kunci
- **CI vs CD**: CI memverifikasi & membuat artefak; CD menaruh artefak itu di lingkungan.
- **Runner self-hosted** diperlukan karena cluster ada di laptop; imbalannya risiko keamanan, maka dibatasi ke `main` dan jangan jalankan kode dari fork.
- **Rolling update** + readiness probe = deploy tanpa downtime; deploy gagal tidak merusak versi yang berjalan.
- **Rollback** cukup satu perintah karena Kubernetes menyimpan riwayat revisi.
